# MASTER DEVELOPMENT PROMPT — SENTINELAI

You are an expert senior software architect, full-stack engineer, ML engineer, cybersecurity engineer, UI/UX designer, and DevSecOps engineer.

Build a **production-quality, fully functional web application** named:

# SentinelAI

### AI-Powered Multi-Modal Digital Threat Detection & Digital Authenticity Analysis Platform

This is a serious high-level software engineering project. Do NOT build a mockup, static frontend, prototype with fake results, or collection of placeholder pages.

---

# 1. CORE CONCEPT

SentinelAI is a unified web-based security analysis platform.

A user should be able to submit suspicious:

* Images
* Videos
* Audio
* Documents
* URLs
* Text/messages
* Files

The platform determines the appropriate analysis pipeline and performs specialized security/authenticity analysis.

The system must support:

1. Deepfake Detection
2. Document Forgery / Manipulation Detection
3. Phishing Detection
4. Scam / Social Engineering Detection
5. Malicious File / Malware Analysis

The individual detection results are then combined into:

**Risk & Evidence Aggregation**

The aggregated findings are passed to a local LLM through:

**Ollama → Llama 3.1 / Qwen3**

The LLM must explain the findings in understandable language and generate recommendations.

Finally:

**Final Security Report**

# 3. MAJOR DETECTION MODULES

## A. DEEPFAKE DETECTION

This is one of the primary features and must receive strong emphasis.

Support:

* Image deepfake detection
* Video deepfake detection
* Audio/voice analysis where feasible
* AI-generated/manipulated media indicators

The system should perform appropriate preprocessing and extract meaningful features.

For images:

* Image metadata
* Compression characteristics
* Visual artifacts
* Face detection
* Face-region analysis
* AI/manipulation indicators

For videos:

* Frame extraction
* Face detection
* Representative-frame analysis
* Temporal inconsistencies where supported
* Frame-level confidence aggregation

For audio:

* Audio extraction
* Basic signal/features analysis
* AI-generated/synthetic voice indicators where an appropriate model is available

The result should not simply say:

"Fake: 87%"

Instead produce structured evidence such as:

* Authenticity score
* Manipulation probability
* Confidence
* Detected faces
* Suspicious regions/frames
* Technical indicators
* Model evidence
* Limitations

The UI should allow users to understand WHY the media was classified as suspicious.

# 4. DIGITAL DOCUMENT / GOVERNMENT DOCUMENT FORGERY DETECTION

Create a dedicated document authenticity analysis module.

This feature is particularly important.

The platform should be able to analyze documents such as:

* Government forms
* Certificates
* Identity-related documents
* Official letters
* Notices
* Scanned documents
* PDFs
* Images of documents

The system should NOT claim legal authenticity or definitively determine whether an official government document is genuine.

Instead, identify:

* Possible visual manipulation
* Inconsistent fonts
* Misalignment
* Copy-paste artifacts
* Image compositing
* Metadata anomalies
* Compression inconsistencies
* Suspicious regions
* Text inconsistencies
* OCR-extracted information
* Formatting anomalies
* Potential tampering indicators

Where applicable, use:

* OCR
* Image preprocessing
* Metadata extraction
* Computer vision
* Document layout analysis
* Image-forensics techniques

The report should clearly distinguish:

"Detected evidence of possible manipulation"

from:

"This document is officially forged."

Avoid unsupported certainty.

# 9. LOCAL LLM — OLLAMA

The application MUST support local LLM inference through Ollama.

Primary models:

* Llama 3.1
* Qwen3

Do not hard-code a single model.

Implement a configurable LLM provider abstraction:

LLM Provider
→ Ollama
→ Selected Model

The user/admin should be able to configure which installed Ollama model is used.

The application should detect available Ollama models where possible.

Example configuration:

OLLAMA_BASE_URL=http://localhost:11434

OLLAMA_MODEL=llama3.1

Allow switching to:

qwen3

The LLM is NOT the primary detector.

It must NOT invent detection results.

The LLM receives structured evidence generated by the detection modules and is responsible for:

* Explaining findings
* Summarizing evidence
* Explaining risk
* Providing recommendations
* Producing human-readable security reports

Use structured prompts and constrained output.

Clearly instruct the LLM:

"Never invent evidence. Only explain evidence supplied by the detection pipeline."
